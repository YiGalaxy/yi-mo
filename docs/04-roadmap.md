# 路线图

每个里程碑以**能跑通的完整用户场景**为验收单位，不以"功能做完"为单位。宁可少做，不可半做——半做的功能比没有更消耗信任。

里程碑同时是学习阶段：每个都标注了对应的技术要点，做完就掌握了那部分。

---

## M0 · 骨架跑通

**场景**：双击启动脚本，浏览器打开，添加一个文件夹作为书库，看到里面已有的稿子列在树上。

| 交付 | 技术要点 |
|---|---|
| Spring Boot 项目骨架 | `@RestController`、`@Service`、配置文件、日志 |
| Vue 3 + Vite + TS 项目骨架 | 组合式 API、单文件组件、`<script setup lang="ts">` |
| 前端代理后端 | Vite `server.proxy` |
| MySQL 连接 + 建表脚本 | JDBC、`schema.sql` 初始化、连接池 |
| MyBatis-Plus 接入 | `@Mapper`、`BaseMapper`、简单查询 |
| `LibraryStorage` | Java NIO、路径安全校验、原子写入 |
| 书库增删查 | REST 设计、DTO、`@RestControllerAdvice` 全局异常 |
| 文件扫描与类型推断 | 目录遍历、frontmatter 解析 |
| 卷章树接口 | 树形数据组装 |

**验收**：添加一个已有稿件的文件夹，树上正确列出所有章节和卷。用 `curl` 打接口能看到正确 JSON。

**学习产出**：理解一个 HTTP 请求从 Vue 组件发出，到 Java 处理，到 MySQL 查询，再回到浏览器的完整链路。这条链路是整个项目的地基。

## M1 · 能写

**场景**：打开一个章节，改几个字，关掉浏览器，重新打开，字还在。用记事本打开那个 `.md` 文件，看到的是干净的 Markdown。

**这是整个项目的分水岭。** 它跑通意味着"作者能写、能存、数据不会丢"成立。在此之前不要碰任何 AI 功能。

| 交付 | 技术要点 |
|---|---|
| Tiptap 编辑器接入 | ProseMirror 文档模型、Vue 组件封装 |
| Markdown ↔ ProseMirror 往返 | 序列化、往返自检 |
| 自动保存 | debounce、`contentHash` 冲突检测、幂等 |
| 新建 / 删除 / 重命名章节 | 文件创建、frontmatter 写入、文件名生成 |
| 拖拽排序 | 前端拖拽库、批量重排接口 |
| 专注模式 | 纯 CSS + 状态管理 |
| 中文排版 | 全角空格缩进、标点处理 |
| 版本快照 | 定时任务、文件副本 |

**验收**：
1. 手改一个字 → 等 2 秒 → 用记事本打开磁盘上的文件，确认改动已落盘
2. 用 Typora 改同一个文件 → 回到亿墨 → 确认检测到冲突并弹窗
3. 往返测试语料库全部通过（`serialize(parse(md)) === md`）

**风险**：Markdown ↔ ProseMirror 往返丢信息。缓解：从第一天起建立往返测试语料库，每发现一个丢失 case 就加一条测试。

## M2 · 好用

**场景**：能连续写作三小时不被打断，能随时查到三个月前写的某句话。

| 交付 | 技术要点 |
|---|---|
| 大纲视图 | 卡片布局、拖拽、Markdown 任务列表解析 |
| 实体管理 | 五类实体、别名、关系、文件生成 |
| 全文搜索 | MySQL `WITH PARSER ngram`、高亮区间计算 |
| 字数统计 | 中文计数规则、增量统计 |
| 快照 diff 与回滚 | 文本 diff 算法 |
| 导出 TXT / Markdown | 流式输出、中文文件名编码（RFC 5987） |
| 主题与排版设置 | CSS 变量、设置持久化到 MySQL |
| 快捷键体系 | 键盘事件、可配置绑定 |

**验收**：用一本 50 万字、300 章的书库实测——打开 < 1.5s，搜索 < 500ms，章节切换 < 150ms。**中文搜索必须能搜到**（这是 ngram 配置正确的唯一证明）。

**学习产出**：MySQL 的实际使用——索引设计、全文检索、分页查询、连接池调优。

## M3 · 校对

**场景**：写完一章，点"校对"，波浪线标出 12 处错字、3 处语病，逐条接受或忽略。

| 交付 | 技术要点 |
|---|---|
| 中文规则引擎 | 12 类规则、纯 Java 实现、单元测试 |
| 批注锚定与重定位 | ProseMirror Decoration、四级重定位算法 |
| 波浪线渲染与修复菜单 | 编辑器扩展、行内 UI |
| Spring AI 接入 | `ChatModel`、流式调用、结构化输出 |
| 模型配置界面 | 表单、连通性测试、密钥存储 |
| LLM 校对 | 分批调用、JSON 解析、片段校验 |
| SSE 流式推送 | `SseEmitter`、前端 EventSource |
| 提案中心 | 批量接受、事务撤销 |
| 降级 UI | 能力状态展示 |

**验收**：
1. 规则引擎在 100 万字语料上误报率 < 2%
2. LLM 返回的片段 100% 能在原文中定位（不能定位的丢弃）
3. 校验 `@Transactional` 与 AI 调用的隔离——用连接池监控确认没有长事务

**风险**：误报淹没作者。缓解：规则默认只开高置信项；LLM 结果按 `confidence` 排序，低置信折叠。提供"这条规则我不想看"的一键关闭。

**学习产出**：这是 AI 应用的核心一课——**大模型不是万能的，该用规则的地方用规则**。规则引擎覆盖七成问题，成本为零，速度是 LLM 的千倍。这个判断力比会调 API 值钱得多。

## M4 · 知识库

**场景**：写完 20 章，知识库面板提示"发现 3 个新人物、5 处人物信息更新"，作者确认后，人物卡自动补全，每段都带出处链接。

| 交付 | 技术要点 |
|---|---|
| 章节摘要生成 | 异步任务、结构化输出 |
| 实体抽取 | 工具调用、JSON Schema 约束 |
| 实体消解 | 别名匹配、LLM 判别、不确定项处理 |
| 待确认面板 | 批量确认 / 合并 / 拆分 |
| 人物卡补全 | 带 `evidence` 的 diff 提案 |
| 关系图 | 力导向图、Vue 组件 |
| 时间线 | 从 `storyTime` + 摘要生成 |
| HanLP 接入 | 中文分词、人名识别（作为无模型时的降级） |
| 任务队列 | `ThreadPoolExecutor`、任务表、进度流 |

**验收**：用一本已有 20+ 章的真人作品，抽取出的人物列表与作者手工整理的人物列表重合度 > 85%，且**错误合并数为 0**。

**风险**：实体消解错误合并。缓解：绝不自动合并，全部走确认。错误合并是最难发现、后果最严重的错误类型。

## M5 · 一致性

**场景**：作者点"全文体检"，报告"第 41 章有 2 处与前文矛盾，有 3 个伏笔埋了 30 章还没回收"。

| 交付 | 技术要点 |
|---|---|
| 一致性检查三种模式 | 长上下文调用、提示词工程 |
| 矛盾报告 UI | 双方原文对照、章节跳转 |
| 忽略列表 | 配置持久化 |
| 伏笔追踪面板 | 状态机、时效量化 |
| 视角一致性检查 | POV 漂移检测 |
| 一键"全文体检" | 批量任务、可中断可续跑 |

**验收**：在 M4 的同一本书上，人工构造 10 处矛盾（改名、时间倒退、设定互斥、死而复生），检出率 > 70%，误报率 < 20%。

**风险**：上下文超限。缓解：分级策略——短篇（< 20 万字）直接全文喂长上下文模型；长篇按卷分批 + 摘要链；超长篇只做实体卡 + 摘要链。

## 明确不做

列出边界比列出计划更能说明项目是什么。

| 不做 | 理由 |
|---|---|
| 用户账号 / 云同步 | 有账号就有服务器，有服务器就有成本和责任。作者用 Git 或网盘同步文件夹即可 |
| 多人协作 | 需要冲突解决和权限模型，与"无账号"根本冲突 |
| 在线托管版本 | 亿墨的设计是读写用户本机磁盘，托管版本做不到这点，且立刻引出账号和数据存储问题 |
| 移动端 App | 长文创作在手机上不成立。响应式保证能查看和改错字即可 |
| AI 全自动写小说 | 亿墨是工具，不是代笔。生成能力一律是"续写建议"，不是"自动成章" |
| 在线社区 / 作品发布 | 与"你的稿子是你的文件"定位冲突，且引入内容审核责任 |
| 富文本花哨排版 | 小说是纯文本的体裁。窄编辑器是为了往返保真，不是功能缺失 |
| Redis / 消息队列 | 本地单用户应用，一个线程池足够 |

## 工程约束

贯穿所有里程碑的要求，不满足则不算完成：

1. **稿件永不损坏**。所有写文件走「临时文件 → 原子重命名」。
2. **数据库可重建**。删掉所有表，除了对话记录和写作统计，其余能从书库文件夹恢复。
3. **无网络也能用**（除 LLM 功能外）。
4. **所有 LLM 功能可关**。关掉后是一个完整好用的本地写作工具。
5. **数据格式向后兼容**。`schemaVersion` 迁移必须有测试覆盖。
6. **核心逻辑有单测**。往返序列化、批注锚定、规则引擎、实体消解、路径安全是测试重点。
7. **接口契约不随意改**。改 `06-api.md` 意味着前后端都要动，先对齐再改。
8. **每个 PR 附带手动验证步骤**。自动化测试覆盖不了的，写清楚怎么点。
